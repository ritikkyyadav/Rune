# Rune v0.1.0

Rune is a terminal coding harness: you choose the model, Rune keeps control of execution,
acceptance checks, recovery and the evidence trail. It runs in your terminal, installs into
`~/.rune`, and never sends anything anywhere except to the model host you configure.

This is the first public version. Everything below is stated as what was verified, what is
experimental, what the platform limits are, and what is unresolved, so that you can decide
what to trust.

## Install

```sh
curl -fsSL https://raw.githubusercontent.com/ritikkyyadav/Rune/main/scripts/web-install.sh | bash
```

Then `rune` to start, `/setup` to choose a provider and model, add a key or sign in, choose
search, a spend cap and a sandbox policy — all inside the terminal, without editing a config
file. `rune doctor` reports the state of the install.

## Verified

- **Install and first run.** A clean machine installs Rune from source on macOS and Ubuntu in
  hosted CI, and the six-step setup runs without a model call; the provider you save is the
  provider the next start uses.
- **The contract.** Every request gets a contract at intake, every run ends with a verdict
  that says what was accepted and what was not, and acceptance is decided by the runtime from
  checks that could have failed — never from the model's own account. Independent acceptance
  files (`--acceptance`) run outside the model's reach and cannot be edited by it.
- **Recovery and interruption.** A run killed mid-tool resumes with its work, its worker's
  work, its contract and its counters intact; orphaned processes die with the engine.
- **Sandboxing.** Tool calls run in an OS sandbox on macOS and Linux; the Linux containment
  audit runs in hosted CI on every push. Credential files under `~/.rune` are denied to
  tool calls.
- **Sub-agents.** Named, budgeted, with their own stream to the parent; a child's patch is
  integrated only against the tree it returns to, and a child cannot grant acceptance.
- **Cost and efficiency.** Per-role accounting of what a run spends; measured reductions in
  reviewer calls and no-op completions on a mock corpus.
- **Memory.** Rune remembers only what you said or what a check proved — never its own
  account of a run. Three modes: `off`, `auto`, `manual` (`/memory update`). Entries are
  signed, carry their provenance, and can be inspected and forgotten with `/memory`.
- **Interface.** One column: your transcript at full width, the composer at the bottom, a calm
  working pulse; the split layout with an agents column is a setting.

## Experimental

- **Self-evolution.** Lessons and playbooks exist behind control cohorts and promotion rules.
  No trial has yet shown held-out improvement with the learning cost counted; treat it as
  controlled experimentation, not demonstrated self-improvement.
- **Visual review.** Frontend work gets a blind, rubric-bound visual record with no numeric
  score. The rubric has not yet been run by an independent reviewer on real work.
- **Comparison arms.** Adapters for OpenCode, Claude Code and Codex exist and are validated
  offline; no live comparison series has been run, so no ranking against them is claimed.

## Platform limits

- macOS and Linux are supported and tested. Linux containment is proven in a privileged
  Docker rig and on hosted CI; ordinary hosts that refuse user namespaces are unmeasured.
- Windows is not supported in this version.
- A browser (Playwright) is optional; without one, visual review is a fetch, not a capture,
  and Rune says so before it spends.

## Unresolved, and stated

- The memory store's integrity depends on its signing key being unreadable by tool calls;
  this version denies those reads in the sandbox and moves the key to the OS credential
  store, and the first real-use scorecard is `rune memory` after a week of sessions.
- Memory's guard is a filter, not a boundary. The check that inspects a remembered line
  before it is promoted catches planted-looking instructions, but it is a list of phrasings,
  and an ordinary paraphrase gets past it: of fourteen freshly worded weakenings, eleven
  survived. We are not claiming otherwise. What holds instead is the runtime: remembered
  text reaches a model as quoted data inside a block that says so, and the boundaries that
  matter (sandbox, permissions, asking, verification, budget, acceptance) are computed from
  the policy, the gear and the ledger by code that has no parameter a remembered sentence
  could arrive through. A test writes a weakening entry straight into a promoted store, past
  every filter, and asserts that no permission decision, containment route, sandbox choice
  or turn budget moves. The guard stays as defence in depth.
- Five adversarial verification passes ran before this release; each found real defects and
  each was fixed. That process continues; findings are recorded in the repository's
  `docs/harness-status.md`.
- Two credential stores (the setup wizard's keychain entry and `/keys`' secrets file) still
  describe themselves differently.
- The controller's repair and delegation policies ship behind keys that default off.
