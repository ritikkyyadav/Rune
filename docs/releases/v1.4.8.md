# Rune v1.4.8

A patch on v1.4.7, and the seventh phase of the reliability plan: shipping like a product.
`rune upgrade` now survives a dropped connection and can roll back, and `rune doctor` checks the
install itself.

## Install or upgrade

```sh
curl -fsSL https://savoir.services/install.sh | bash
```

An existing install can run `rune upgrade`.

## What changed

- **`rune upgrade` survives a dropped connection.** On 15 October it failed twice with ECONNRESET:
  the Mac's lid was shut, it woke for seconds at a time, and one interrupted fetch ended the whole
  upgrade. A download now keeps what it received and asks for the rest (`Range`), up to six tries
  with a growing pause. It starts over only when the server will not resume. The checksum check
  after it is unchanged, so a bad splice is never installed.

- **Rolling back, pinning, and a slower channel.**

  | Command                         | What it does                                                 |
  | ------------------------------- | ------------------------------------------------------------ |
  | `rune upgrade --rollback`       | Swaps back to the build kept as `.backup`; again to undo     |
  | `rune upgrade --to <version>`   | Installs that release, older or newer, checksum-verified     |
  | `rune upgrade --channel stable` | Installs the newest release that has been out for seven days |

  A rollback is renames only: instant, and no network.

- **`rune doctor` checks the install itself.** It now reports:
  - whether the binaries' code signatures hold (macOS kills a binary whose signature broke, at
    launch, with no message);
  - whether there is a build to roll back to;
  - how much the old builds kept by source installs weigh;
  - whether the session database passes `quick_check`.

- **`rune doctor prune-backups`** shows what removing all but the newest three old builds would
  reclaim. On the founder's machine that is 62 installs and 5.0 GB. It is a dry run, and
  `--apply` removes them. The plain `.backup` that `--rollback` uses is never touched.

- **`RUNE_SUSPEND_CLOCK=off` turns off the sleep check** (1.4.4) for a process. The test suite
  sets it: every test file shares one process, and on Windows CI a test that blocked the event
  loop for 40 seconds looked like a sleep to the next file's runs, which then re-sent failures
  free. Tests that exercise the check pass their own clock.

## Checked, and stated

- The download was driven with a stream that drops mid-transfer:
  - it resumed from the byte it had, with the `Range` header asked for;
  - a server that sent the whole file again was handled;
  - a 404 was not asked for twice;
  - a connection that never held gave up after six tries, installing nothing.
- `--rollback` was run twice on a real folder: it swapped, then swapped back, leaving nothing
  behind. `--to` installed an older release. `--channel stable` passed over a two-day-old
  release and a prerelease.
- The doctor's new checks ran against the founder's real install, read-only: signatures valid, a
  rollback available, the old builds' weight, and the database intact. Its database check was
  also given a file with a damaged page, which it reported.
- **13 deliberate breakages, all caught**, including a resume that asks for the whole file, a
  404 retried, a rollback that swaps only one binary, a stable channel that ignores age, and a
  database check that calls any database intact. The last one was first missed and the test that
  catches it was added.
- **Suites:** unit 7,968 passed and 0 failed; integration 488 and 0; the scripted evaluation 63
  of 63.
- **CI found two Windows-only problems in this release's first run, both fixed before the tag.**
  A folder a SQLite file was open in could not be removed. And a test that blocked the event loop
  for 40 seconds made later runs in the same process look as if the machine had slept. Both were
  reproduced on macOS before the fix: blocking for 35 seconds failed three transport tests with
  the shared clock on, and none with it off.
- This release was tagged only after CI passed on its own commit: macOS, Linux and Windows.

## Known, and stated

- **No versions directory.** Rollback works without one; changing the install layout on the one
  machine Rune runs on is a risk this release does not take.
- **The old builds are still there** until the founder runs `rune doctor prune-backups --apply`.
  That is decision D5, and it is theirs.
- **A minimum-version floor** waits for a release that needs one.
