# Rune v1.4.7

A patch on v1.4.6, and the sixth phase of the reliability plan: long commands keep their work. An
install, a test suite or a build that runs past its timeout is handed over as a background shell
instead of being killed, and background shells have lifetimes.

## Install or upgrade

```sh
curl -fsSL https://savoir.services/install.sh | bash
```

An existing install can run `rune upgrade`.

## What changed

- **A long command that reaches its timeout keeps its work.** A foreground command that ran past
  its timeout used to be killed with its whole process group. One install's record has 30 of them
  between July and October, and most were commands whose run time is the work: `npm install` six
  times, `bun test` three, a `pip install`, a `playwright install`, an `ollama pull`, a typecheck.
  An install killed at two minutes leaves a half-written `node_modules`, and the next attempt
  starts over.

  Installs, test suites, builds, type checks and downloads now start as a background shell. They
  get the same launch decision and the same sandbox as foreground bash, and the call waits as long
  as it did before.
  - **If the command finishes in time**, the result is the ordinary foreground result.
  - **If it is still running**, it is not stopped: the result gives the shell id and the output so
    far, the model reads the rest with `bash_output`, and the result says when a `cd` inside the
    command does not carry over to the next one.

  Every other command runs exactly as before. A command that starts with `sleep` is never handed
  over. On Windows, long commands still run in the foreground: a background shell there is
  `bash -lc`, and Rune has no Windows shell contract yet.

- **Background shells have lifetimes.** A shell Rune handed over itself is stopped after 30
  minutes. In a headless run (`rune -P`), where nobody is watching, every background shell is.
  `bash_output` says when a shell was stopped at its limit rather than by `kill_shell`, and every
  shell is still reaped when Rune exits.

## Checked, and stated

- The hand-over was driven with real `make` targets through the real bash wrapper:
  - a target that finishes in time gave a foreground result and left no shell behind;
  - a target that outlived a 400 ms timeout was handed over, kept running, and finished, read
    through `bash_output`;
  - Esc while waiting stopped it.
- The matcher was checked against the commands that timed out in the record, and against ordinary
  ones that must not match (`ls`, `git status`, `echo npm install`, a server started with
  `python3 -m http.server`).
- **12 deliberate breakages, all caught.** These included:
  - a timed-out command killed after all;
  - a finished run leaving its shell behind;
  - a handed-over shell with no lifetime;
  - the unattended default ignored;
  - Esc leaving the command running.
- **Suites:** unit 7,947 passed and 0 failed; integration 488 and 0; the scripted evaluation 63
  of 63.
- This release was tagged only after CI passed on its own commit: macOS, Linux and Windows.

## Known, and stated

- **A shell's two streams arrive as one.** A handed-over command's output is in `stdout`, in the
  order it was printed; `stderr` is empty.
- **Only these shapes are handed over.** A long command that is none of them (a custom script, a
  server started in the foreground) still stops at its timeout, as before; `run_in_background`
  is the way to start one.
- **No live run has exercised this yet**; the live sitting (R8) is where it is measured.
