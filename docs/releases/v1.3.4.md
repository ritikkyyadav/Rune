# Rune v1.3.4

A patch on v1.3.3. It fixes a rule that 1.3.2 introduced and that did not work in an ordinary
terminal.

## Install or upgrade

```sh
curl -fsSL https://savoir.services/install.sh | bash
```

An existing install can run `rune upgrade`.

## What changed

- **A test that was already failing is left alone, in a real project's suite.** When a check goes
  red, Rune compares the failing tests with the tree the run started from, and a failure that was
  already there is reported and not handed to the agent. Since 1.3.2 that did not happen for a Bun
  suite of more than about twenty tests, in a terminal or inside GitHub Actions. Bun closes such a
  run by listing its failures a second time; Rune read that list as more failures, found more of
  them than the totals gave, and refused to compare. The agent was then asked to repair tests it
  had never touched. In one measured run it did so by rewriting the project's own `test` script.
  If you run Rune on a Bun project, upgrade.

- **When Rune cannot tell whether a failure was already there, it says why.** The reason was
  worked out and thrown away. It is now in the notice you see, on the `verification_completed`
  event as `attributionUnknown`, and in the saved task state.

- **A run that ends before its background reviewer answers says so.** In Auto mode ordinary
  actions run at once and a reviewer reads them in the background. `rune -P` exits when its work
  is done and does not wait for that reviewer, so an action still waiting was never answered for,
  and its audit row went on saying it was allowed under supervision. Rune now writes a row for
  each such action when it closes. Exit takes no longer and no reviewer is called. `rune doctor`
  and `rune audit` print how many actions ran with no background review; that count had been
  taken and never shown.

- **`rune upgrade` over a source install no longer leaves Rune telling you to rebuild.**

The full list is in [`CHANGELOG.md`](../../CHANGELOG.md).

## Checked, and stated

- **How the first fault was found.** A live run from 2026-10-07 was replayed through a real
  `rune -P` process, with a scripted model in place of a provider. Before the fix the replay was
  asked for a repair, and gave the reason "something failed that the report does not name as a
  test". After it, the two failing tests are named as already failing, no repair is asked for,
  and the project's files are left as they were.
- **Why no test had caught it.** Bun prints a shorter report, with no closing list, when it thinks
  an agent is reading. The tests for this rule ran in such a shell, on two test files. There are
  now two more: Bun's closing list word for word, and thirty real test files read through the
  report a terminal gets.
- **A first comparison on hard tasks, made on 1.3.3.** Three tasks drawn from Rune's own history,
  Rune against OpenCode on the same model. Both passed every hidden check with no regression.
  Rune made fewer model calls on all three at about the same list cost, and took longer on two.
  Three pairs is half of what a score needs, so there is no score.
- This release was tagged only after CI passed on its own commit: macOS, Linux and Windows.

## Known, and stated

- **Rune can call finished work unfinished.** In that comparison all three runs passed everything
  and ended with Rune's own verdict saying "unmet" or "partial". With no criteria stated for a
  task, "unmet" is what the verdict is built to say; it reads as a failure, and it is not one.
  Not changed in 1.3.4.
- **The check at the end of a turn gives up after 120 seconds.** On a project whose suite takes
  longer it waits the full time and measures nothing. Seen on two of the three runs. Not changed
  in 1.3.4.
- A background review that _fails_ — the reviewer cannot be reached, times out, or gives an
  answer that cannot be read — still leaves no audit row.
- The "already failing" rule reads Bun's test report only. Under another test runner the answer
  is "unknown", and the failure is handed to the agent as before.
- On Windows, Rune cannot yet rebuild the tree a run started from when the project has installed
  dependencies or other git-ignored files to carry over. It says the answer is unknown there.
- The fixes in this release were checked by replay and by test. None was measured in a live run.
