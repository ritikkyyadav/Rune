# Rune v1.4.4

A patch on v1.4.3, and the third phase of the reliability plan: the connection to the provider. A
laptop that sleeps no longer ends a run, a response cut partway keeps the tool calls it finished,
and a prompt over the model's window is never sent again unchanged.

## Install or upgrade

```sh
curl -fsSL https://savoir.services/install.sh | bash
```

An existing install can run `rune upgrade`.

## What changed

- **A laptop that sleeps no longer ends a run.** On 12 October the lid closed over a research run
  at 01:21. Every failure that run recorded fell inside the dark wakes that followed: the few
  seconds a closed Mac runs between sleeps, with no network (`pmset -g log`, read beside Rune's own
  incident record). Each failure spent the run's error budget. The outage clock ran through the
  sleep, so at 01:49, the third dark wake, the run ended `provider_lost`: "3 consecutive errors,
  600s unanswered". Now:
  - a call cut by a sleep, or started within 30 seconds of a wake, does not count as an error and
    does not run the outage clock;
  - it is sent again only once the machine has been awake for 10 seconds straight, so a closed
    lid's dark wakes are waited through instead of failed in;
  - free re-sends are bounded: 3 per wake and 50 per run, so a clock that misreads cannot keep a
    dead provider's run going;
  - the notice says how long the computer slept, and the incident record says `provider.slept`.

- **A response cut after it finished tool calls keeps them.** A stream that failed partway used to
  be re-sent from zero, even when the model had already finished tool calls in it, so a long think
  or a long file was paid for and written twice. Now the run carries out every call the response
  finished, drops the half-sent one and any text after the last finished call, and continues from
  the results. The notice says how many calls were kept. A response that failed before it
  finished any call is re-sent from zero, as before.

- **An over-limit prompt is never sent again unchanged.** When the provider refused the prompt as
  over the model's window and compacting the conversation could not make it fit, Rune re-sent the
  identical prompt until the error budget ran out. The run then ended `provider_lost`, blaming a
  provider that was answering. It now ends at once with an error that says what to do: resume in
  a fresh session from the handoff, or use a model with a larger window. In `rune -P` that is
  `max_tokens`, exit 4.

## Checked, and stated

- The sleep rule was driven through the real agent loop with a probe standing in for the clock:
  - a slept call is re-sent and the run finishes, whether the failure was thrown or reported by
    the stream;
  - a call started 15 seconds after a wake is the sleep's, and one started 45 seconds after is
    not;
  - the re-send waits until the machine has been awake 10 seconds;
  - the bounds hold: 3 per wake, then a failure counts again, and at most 50 per run.

  The clock itself was driven by hand: a late timer is not a sleep, a sleep before a call is not
  the call's, and a wake that just ended is seen before any timer fires.

- The cut was driven through the real gateway and the real loop: only the finished call runs, the
  next request carries its result and never the cut one, and a user's cancel is still a cancel.
- **30 deliberate breakages, all caught.** Each of the following turned tests red: no grace after
  a wake, no wait before the re-send (on either failure path), no bound per wake or per run, a cut
  with nothing finished, an unfinished call kept, and an over-limit prompt re-sent.
- **Suites:** unit 7,885 passed and 0 failed; integration 485 and 0; the scripted evaluation 63
  of 63.
- This release was tagged only after CI passed on its own commit: macOS, Linux and Windows.

## Known, and stated

- **No live run has slept on this build yet.** The dark-wake story is from the record of 12
  October, and the fix was checked against a stand-in clock, not a closed lid. The live sitting
  (R8) includes a run with the lid closed for five minutes.
- **The over-limit path has not been seen live.** This install's record holds no such refusal; the
  path was found by reading the code.
- **Not in this release, and why:**
  - **one retry ladder** (ten attempts, 0.5 s to 32 s, three kinds of 429): the outage deadline
    already bounds the total wait, and changing retry counts without live measurements risks
    longer hangs;
  - **a response cut after text alone** is still re-sent from zero, and a stall gets no per-phase
    rule; continuing from half an answer needs the live sitting to judge;
  - **shrinking `max_tokens`** on an over-limit refusal: reading each provider's wording for the
    input and output split is provider-specific.
