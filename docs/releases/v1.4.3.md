# Rune v1.4.3

A patch on v1.4.2, and the second phase of the reliability plan: a run says how it ended. The exit
code now reports execution, and a provider's usage cap is reported as a pause with a reset time,
not as a lost provider.

## Install or upgrade

```sh
curl -fsSL https://savoir.services/install.sh | bash
```

An existing install can run `rune upgrade`.

## What changed

- **The exit code of `rune -P` says how the run ended.**

  | Code          | Meaning                                                                      |
  | ------------- | ---------------------------------------------------------------------------- |
  | 0             | finished: the model ended its turn                                           |
  | 1             | failed: an error, a stall, a stopped loop, open planned steps, a safety halt |
  | 3             | needed permission and had nobody to ask                                      |
  | 4             | stopped at a limit: turns, output tokens or budget                           |
  | 5             | the provider could not go on: a usage cap, or lost after the retries         |
  | 130           | cancelled                                                                    |
  | 129, 130, 143 | a signal's own code, which wins over everything above                        |

  Whether the task was met is still the envelope's to say: `ok`, `verdict` and `shortfall`, which
  mean what they meant before. Until this release a finished run whose own verdict was `partial`
  or `unmet` exited 1, the same code as a crash, and every live run in the October sittings did
  that on work that passed every hidden check. **If a script relied on that exit 1, pass
  `--strict-verdict`**, which keeps the old rule. The envelope also gains `subtype` (`success`,
  `error_max_turns`, `error_quota`, `error_provider`, …). `rune --help` now lists the headless flags,
  and [`docs/ci.md`](../ci.md) has a table of every way a run ends and what to do about each.

- **A usage cap is named as one.** Until now a plan or usage cap ended a run as `provider_lost`.
  In one install's record, 39 of the 44 runs that ended that way had hit a Codex limit with a known
  reset. The gateway already knew the difference; the run now keeps it:
  - the run ends `quota_wall`, and the reset is carried as `resumeAt`;
  - the closing row reads "paused at the provider's usage limit -- it resets at HH:MM" instead of
    "stopped on an error";
  - the TUI's auto-resume and `--resume-until` wait for that exact time.

  A refusal that is not a cap still ends `provider_lost`.

## Checked, and stated

- The cap path was driven through the real agent loop with a gateway sending exactly what the
  real one sends (`usage_cap` and `resetAt`): it ends `quota_wall` with the reset, hands off as a
  quota wall before the error, and still stops on the first capped turn without waiting.
- Every ending has a test for its exit code and subtype, and six deliberate breakages each turned
  tests red: a cap not treated as a wall, the cap's code dropped again, a quota exit of 0, the
  strict rule ignored, the reset ignored on resume, and the pause row removed.
- **Suites:** unit 7,844 passed and 0 failed; integration 485 and 0; the scripted evaluation 63
  of 63.
- This release was tagged only after CI passed on its own commit: macOS, Linux and Windows.

## Known, and stated

- **The verdict itself is unchanged.** A finished run can still report its work as `partial`
  when it could not show terms it wrote for itself. That no longer makes the run exit 1; making
  the verdict reach `met` when the evidence is there is separate work.
- **A run stopped with its own planned steps open still exits 1** (`error_open_steps`). That is
  the loop ending the run, not a verdict.
- No live run has hit a quota wall on this build yet. The ending was checked with the gateway's
  real event shape, not against a live Codex cap.
