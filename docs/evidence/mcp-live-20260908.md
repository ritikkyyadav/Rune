# MCP, live — 2026-09-08

Rune's MCP client is about four thousand lines: stdio framing, Streamable HTTP,
the legacy SSE pair, OAuth 2.1, pagination, progress, cancellation, elicitation.
Until today every test of it spoke to a mock this repository also wrote — and a
mock agrees with the client about the protocol by construction, which is exactly
the thing that needed checking. The only live attempt on record was the
founder's own `~/.rune/mcp.json`, pointed at a directory whose name has a typo
in it; it produced a connector-down notice and nothing else.

This is the record of driving the real client — `packages/tool-registry/src/mcp/client.ts`,
no stubs, no fakes — against the reference servers the MCP project publishes.
All of them are free and run locally.

Reproduce with `bun test tests/integration/mcp-live-servers.test.ts` (needs
`npx`, the network on a cold cache, and a free loopback port; it skips cleanly
when it has none of them).

## What broke, and what was fixed

**The legacy SSE fallback did not exist.** `transport.ts` carried a comment
saying "HttpTransport falls back to this when a server rejects the streamable
handshake in the way an older one does. Nobody should have to know which vintage
their connector is." Nothing did. `SseTransport` was 170 lines of exported,
untested, never-constructed code, and a URL pointing at a 2024-11-05 server
failed with `MCP HTTP 404` and stayed failed.

The cause was that `HttpTransport` threw a bare `Error("MCP HTTP 404: …")`, so
nothing upstream could tell a 404 from a 500 without parsing the sentence back
apart. Fixed by giving the transport a typed `McpHttpStatusError` carrying the
status, and by having `McpClient.start()` retry once as SSE on 404/405/406 —
the three ways a server says "not this method, not this route". A 500 is a
server that understood us and broke, and is not retried in another dialect.
Verified above: a plain `/sse` URL now connects, and `client.dialect` reports
`sse` so `/mcp` and `rune mcp doctor` can say which protocol is actually in use.

**A connector that never started could not be reconnected.** `McpDiscovery.reconnect`
returned `false` forever for any server with no client — which is every server
whose command or path was wrong. Fixing the typo therefore needed a restart of
the whole session. `discover()` is now built out of a `startServer()` step that
`reconnect()` also uses, so `/mcp reconnect <name>` starts a connector that has
never been up.

**Nothing checked the config before spawning.** See the next section.

Nothing else in the client had to change. The handshake, version negotiation,
pagination, the concurrency gate, stderr draining, response-size limiting,
progress routing and image attachment all worked against real servers on the
first attempt.

## The founder's typo, diagnosed

`~/.rune/mcp.json` points `@modelcontextprotocol/server-filesystem` at
`/Users/ritikyadav890/Projects/Alan`. The directory is `/Users/ritikyadav890/Project/Alan`.
What a session reported was the server's own stderr — a process exited, code 1 —
which describes the symptom and not one word of the cause, even though the cause
was checkable from the config alone in microseconds.

`rune mcp doctor`, run against a fixture that reproduces the entry (the
founder's own file was not modified):

```
    rune mcp doctor

    Config
      user       <RUNE_HOME>/mcp.json
      workspace  <workspace>/.rune/mcp.json

    Credentials  plaintext file (~/.rune/credentials.json)
      ↻ no OS keychain — tokens are in a 0600 file

    Connectors
      files            up 14 tools · stdio · 2025-06-18
      nocmd            misconfigured — "rune-no-such-binary-xyz" is not on PATH
        fix: install rune-no-such-binary-xyz, or give the full path in mcp.json
      typo             misconfigured — /Users/ritikyadav890/Projects/Alan does not exist
        fix: did you mean /Users/ritikyadav890/Project/Alan

    ✗ 2 connectors need attention
```

And `rune doctor` says it in one line without starting anything:

```
  ✗ mcp: 2 misconfigured — nocmd: "rune-no-such-binary-xyz" is not on PATH (install …)
    typo: /Users/ritikyadav890/Projects/Alan does not exist — did you mean /Users/ritikyadav890/Project/Alan
```

A clean workspace gets the quiet version:

```
  ✓ mcp: 3 connectors configured, none misconfigured — live health: rune mcp doctor
```

The suggester is deliberately conservative: it walks the path from the deepest
ancestor that exists and only accepts a sibling within an edit distance a typo
would explain, so `Projects` → `Project` is offered and `Documents` → `Project`
is not. A confident wrong suggestion is worse than none.

The skip path matters as much as the pass: a suite that goes red because a
machine has no network is a suite people learn to ignore. The probe starts a
real server rather than checking `npx --version`, because every cheaper proxy
lies — `npx --version` succeeds offline, and a registry ping succeeds behind a
proxy that then refuses the tarball.
